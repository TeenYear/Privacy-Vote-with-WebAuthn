# Privacy Vote — Anonymous Voting with Zero-Knowledge Proofs

> [中文版](./README_CN.md)

Privacy Vote combines **WebAuthn passwordless authentication**, **Noir zero-knowledge circuits**, and **Solidity smart contracts** to build a "verified yet anonymous" voting pipeline:
voters can prove they are legitimate KYC-approved users without revealing *who* cast *which* vote.

## Key Features

| Feature                              | Description                                                                                       |
| ------------------------------------ | ------------------------------------------------------------------------------------------------- |
| **Zero-Knowledge Proofs**      | PLONK circuit written in Noir — voters prove eligibility without revealing identity              |
| **WebAuthn Authentication**    | Passwordless registration and login via fingerprint, Face ID, or hardware security key            |
| **Deterministic Wallets**      | Ethereum wallet derived from WebAuthn signature — same user always maps to the same address      |
| **Merkle Tree Membership**     | 32-level incremental binary Merkle tree manages verified users, supporting ~4.3 billion entries   |
| **Nullifier Anti-Double-Vote** | Each user–proposal pair produces a unique Poseidon-based nullifier hash to prevent repeat voting |
| **On-Chain Verification**      | PLONK verifier contract auto-generated by Noir and deployed on-chain; results are tamper-proof    |
| **Automatic Address Sync**     | After contract deployment, the new address propagates to both front-end and back-end config files |

### 1. Registration & KYC

```
Browser                          Server                     Contract
  │                                │                          │
  │── WebAuthn create credential ──→                          │
  │   (fingerprint/Face ID/key)    │                          │
  │                                │                          │
  │── WebAuthn auth signature ────→ │                          │
  │   derive deterministic Wallet  │                          │
  │   commitment =                 │                          │
  │     Poseidon2([secret, nulifier]) │                       │
  │                                │                          │
  │── POST /request-kyc ─────────→ │                          │
  │   { username, userAddress,     │                          │
  │     commitmentHash }           │                          │
  │                                │── registerMultipleUsers() ──→ │
  │                                │   (admin operation)      │
  │                                │                          │── insert Merkle leaf
  │                                │                          │── emit UsersRegistered
  │                                │←── leafIndex ────────────│
  │←── { success, leafIndices } ───│                          │

  │ Store in localStorage:         │                          │
```

### 2. Zero-Knowledge Voting

```
Browser                          Server                     Contract
  │                                │                          │
  │── GET /results ──────────────→ │                          │
  │←── 20 candidate list ─────────│                          │
  │                                │                          │
  │   User selects 1 candidate     │                          │
  │                                │                          │
  │── GET /merkle-proof/:idx ────→ │                          │
  │                                │── createProof(idx) ────→ │
  │                                │←── siblings + indices ──│
  │←── proofSiblings + pathIndices │                          │
  │                                │                          │
  │── compute nullifierHash =      │                          │
  │   Poseidon2([nulifier, proposalId])                       │
  │                                │                          │
  │── Noir WASM generates PLONK proof                         │
  │   public: root, nullifierHash, proposalId, voteType=1     │
  │   private: nulifier, secret, siblings, pathIndices        │
  │                                │                          │
  │── POST /vote ────────────────→ │                          │
  │   { proofBytes, publicInputs } │                          │
  │                                │── vote(proof, inputs) ──→ │
  │                                │                          │── UltraVerifier.verify()
  │                                │                          │── check nullifier unused
  │                                │                          │── check root valid
  │                                │                          │── tally (votesFor++)
  │                                │                          │── emit ProposalVoted
  │                                │←── tx receipt ───────────│
  │←── { success } ────────────────│                          │
```

## Usage Guide

### 1. Register

1. Open http://localhost:3000
2. Enter a username
3. Click **Register to Vote**
4. Complete the WebAuthn prompt (fingerprint / Face ID / security key)

### 2. Request KYC

1. Enter your registered username
2. Click **Request KYC**
3. Complete WebAuthn authentication again
4. Behind the scenes:
   - A deterministic Ethereum wallet is derived from your WebAuthn signature
   - A Poseidon commitment hash is computed
   - The back end registers you into the smart contract's Merkle tree
   - Your `leafIndex`, `secret`, and `nulifier` are saved in browser localStorage

### 3. Vote

1. The page automatically fetches a list of 20 candidates from the back-end `/results` endpoint
2. Select **1 candidate** from the candidate grid
3. Click **Submit Vote** — the browser will:
   - Fetch the 32-level Merkle proof path via the back-end `/merkle-proof/:leafIndex` endpoint
   - Compute `nullifierHash = Poseidon2([nulifier, proposalId])`
   - Generate a PLONK zero-knowledge proof using the Noir WASM backend (instance cached for speed)
   - Send the proof to the back end `/vote` endpoint, which forwards it to the contract for on-chain verification and tallying
4. After successful submission the page refreshes candidate vote counts automatically

> The first proof generation takes some time (~30 s to load the WASM backend). Subsequent calls are significantly faster thanks to caching.

## Zero-Knowledge Circuit

The circuit lives at `packages/zkp/circuits/src/main.nr`, with a mirror copy at `packages/client/src/circuit/src/main.nr`.

### Inputs

| Visibility | Name                     | Description                                           |
| ---------- | ------------------------ | ----------------------------------------------------- |
| Public     | `root`                 | Current Merkle tree root                              |
| Public     | `nulifierHash`         | Poseidon2([nulifier, proposalId]) — anti-double-vote |
| Public     | `proposalId`           | Proposal identifier                                   |
| Public     | `voteType`             | Vote type (always 1 = for)                            |
| Private    | `nulifier`             | User's private nullifier                              |
| Private    | `secret`               | User's private secret                                 |
| Private    | `proofSiblings[32]`    | Merkle proof sibling nodes                            |
| Private    | `proofPathIndices[32]` | Merkle path direction flags (0 = left, 1 = right)     |

### Verification Logic

```
1. Compute leaf hash
   leaf = Poseidon2([nulifier, secret])

2. Verify nullifier hash
   assert Poseidon2([nulifier, proposalId]) == nulifierHash

3. Merkle membership verification (32 rounds)
   for i in 0..32:
       if proofPathIndices[i] == 0:
           hash = Poseidon2([hash, proofSiblings[i]])
       else:
           hash = Poseidon2([proofSiblings[i], hash])

4. Assert final hash equals the public root
   assert hash == root
```

This guarantees that the prover knows a valid `(nulifier, secret)` pair whose corresponding leaf exists in the current Merkle tree — without revealing *which* leaf.

## Smart Contracts

### ZK_KYC.sol — Main Contract

Inherits from `CryptoTools` (Merkle tree operations).

| Function                                                           | Access              | Description                                         |
| ------------------------------------------------------------------ | ------------------- | --------------------------------------------------- |
| `requestRegistration(username, commitment)`                      | Anyone              | User submits a registration request                 |
| `registerUser(username)`                                         | Admin only          | Approve a single user, insert Merkle leaf           |
| `registerMultipleUsers(usernames[], addresses[], commitments[])` | Admin only          | Batch approval, emits `UsersRegistered`           |
| `createProposal(username, description, data)`                    | Authenticated users | Create a voting proposal                            |
| `vote(proof, publicInputs[])`                                    | Anyone              | Submit ZK proof vote; contract verifies and tallies |
| `batchVote(proofs[], publicInputs[][])`                          | Anyone              | Batch voting                                        |
| `getVoteStatus(proposalId)`                                      | View                | Query proposal vote data                            |
| `getCurrentRoot()`                                               | View                | Get current Merkle root                             |
| `createProof(leafIndex)`                                         | View                | Get Merkle proof path for a given leaf              |

### CryptoTools.sol — Merkle Tree Infrastructure

- 32-level incremental binary Merkle tree
- Maintains a history of the last 32 roots (`isValidRoot()` handles concurrency)
- Uses Poseidon T3 as the tree node hash function

### Library Contracts

| Contract                  | Purpose                                                                  |
| ------------------------- | ------------------------------------------------------------------------ |
| `plonk_vk.sol`          | Noir-generated PLONK verifier — exposes `verify(proof, publicInputs)` |
| `PoseidonT2.sol`        | Poseidon hash (1 input)                                                  |
| `PoseidonT3.sol`        | Poseidon hash (2 inputs) — used in Merkle tree                          |
| `InternalBinaryIMT.sol` | Low-level incremental Merkle tree with pre-computed zero values          |
| `Constants.sol`         | BN254 scalar field modulus, max tree depth (32)                          |

## Privacy Model

### 1. Identity–Vote Separation

During registration, only a Poseidon commitment hash (`Poseidon2([secret, nulifier])`) is stored on-chain — not the username or address. When voting, the submitted zero-knowledge proof only attests that "the prover's leaf exists in the Merkle tree," without revealing *which* leaf.

### 2. Nullifier Anti-Double-Vote

Each vote produces `nullifierHash = Poseidon2([nulifier, proposalId])`. The contract records used nullifier hashes: a second vote on the same proposal is rejected. Because the nullifier itself is a private input, an outside observer cannot link votes across different proposals to the same person.

### 3. Merkle Tree Privacy

Users never need to reveal their commitment value or leaf index on-chain. They prove membership via the Merkle proof path (a private input). The root is public, but it is computationally infeasible to determine who voted from the root alone.

### 4. Zero-Knowledge Guarantee

The zero-knowledge property of PLONK proofs ensures that verifiers (the contract and all on-chain observers) learn nothing beyond "this vote is valid and has not been cast before."

## FAQ

**Q: Does the contract address change after every redeployment?**
A: Yes. However, the `deploy:contracts` script automatically syncs the new address to both front-end and back-end config files. Simply restart the services — no manual edits needed.

**Q: Can I run this on a live Ethereum network?**
A: The current setup targets local development. For testnet or mainnet deployment:

- Change `RPC_URL` to the appropriate network endpoint
- Use a private key with real funds
- Remove or adjust the `--code-size-limit` flag on Anvil (or ensure the contract fits within EIP-170)
- Configure an appropriate gas strategy

**Q: WebAuthn registration fails?**
A: Verify that:

- You are accessing the app via `https://` or `http://localhost` (WebAuthn requires a secure context)
- Your browser supports WebAuthn (Chrome, Firefox, Safari, Edge all do)
- Your device has biometric or security key hardware available

**Q: Zero-knowledge proof generation is slow?**
A: This is expected. PLONK proof generation involves substantial polynomial arithmetic. The first call loads the WASM backend (~30 s); subsequent calls are significantly faster thanks to caching. The browser uses multi-threaded WASM acceleration.

**Q: `pnpm` doesn't work on Windows?**
A: PowerShell execution policy may block the `.ps1` wrapper script. Use `pnpm.cmd` instead.
